# Level 255 and rebirth on the original NES Tetris cartridge

The bot plays Nintendo's original Tetris (USA, NTSC, A-Type) in the MesenCE 2.2.1
emulator from level 18, using only controller input through the real menus: no
ROM, RAM or random-number edits, no savestates in play. Every result is checked by
replaying the full recorded input in a fresh emulator and matching RAM, picture,
CPU/PPU clocks and the final result exactly.

Results so far (details in [RESULTS-255.md](RESULTS-255.md)):

- **20 verified games reached level 255** (3,290 lines), every one with the score
  maxed at 999,999 around level 66 and an uncapped ("theoretical") score of
  about 22.1–22.5 million.
- **One verified rebirth game**: level 255, the level counter wraps to 0, then back
  up to level 255 again (absolute level 511, 6,651 lines, uncapped score 43,047,996).
- Current bot (v8c): 6 of 7 development games reached 255; a crash-zone simulator
  that reproduces real games move for move estimates about 94–95% per game.

## Why level 255 is hard on the original cartridge

The game has no ending: after level 255 the 8-bit level counter wraps to 0. Two
things stop a run long before that:

1. **Top-outs at level-29 speed.** From level 29 on, pieces fall one row per frame.
2. **Crash bugs from level 155.** After a line clear the score routine runs long,
   and its 8 jump-table calls can be interrupted by the frame interrupt (NMI), which
   corrupts a jump target and sends the CPU into RAM. Whether a clear crashes depends
   on the level, the line count, how many lines and which rows are cleared, the
   soft-drop "pushdown" points, the count of that clear type so far, and a little
   unobservable timing jitter. Zero-line locks matter too at levels 247–255. The
   danger zones are roughly levels 154–173 and 247–255, and they recur on every lap.

## How the bot plays

Entry point: `python -m nes_original.endurance --selector tuned-crash-map ...`
(see `nes-bot/tools/run255.sh` for the full current configuration).

- **Controller** (`nes_original/feedback.py`): legal timed inputs, 30 taps per second
  (press/release every other frame, the fastest the game registers), rotation every
  4 frames, planning time charged as real frames.
- **Move evaluation** (`nes_original/sim.py`, `TunedSelector`): Dellacherie board
  features, plus the visible next piece (beam 5) and, in danger zones, an average over
  all 7 unknown pieces after it (expectimax). Level zones swap in other weights:
  no-singles weights at 156–158, low-stack weights at 246–249. In zones where some
  clears are dangerous, the lookahead also avoids planning those clears (168–173), and
  at 249/253/255 it avoids next-piece placements that would need pushdown they cannot get.
- **Crash avoidance** (`nes_original/crash_model.py`, `CrashMapPrioritizer`): every
  candidate line clear from level 150 is rated with the exact crash model
  (`nes_original/crash_cycle_model.py`, a Python port of HydrantDude's TetrisGYM model,
  validated on 986/988 community sheet cells and the observed real crashes). The bot:
  - plays the safest surviving move; a flagged move only if every survivor is flagged;
  - decides **per move** whether to hold Down: Down is normally off from level 155
    (pushdown shifts crash timing), but a clear may keep it when the model rates the
    pushdown safer (e.g. a single entering level 158: 100% crash without, 0% with);
  - accepts a partly risky clear when its stack is high (11+ rows ≤ 30%, 14+ ≤ 50%,
    17+ ≤ 90%), because a top-out is certain loss;
  - takes clears whose type count would end in 0 early, where they are safe;
  - avoids "trap" line counts just before a level change when the entering single
    is dangerous (e.g. 1,489 lines at level 154);
  - at 249/253/255 needs a predicted pushdown of 3+ for zero-line non-T/J locks
    (real pushdown measured 0–1 below the prediction).
- **Warm-up**: all compiled code paths run once before the game (`sim.warm_paths`);
  a first compile mid-game once cost a 2.4 s stall and a game.

## Running it

```bash
sh nes-bot/tools/run255.sh 19211            # one game to level 255, then replay verification
sh nes-bot/tools/run255.sh 19211 511        # rebirth: back up to level 255 on the second lap
sh nes-bot/tools/run255.sh 19211 endless    # until the bot tops out or crashes
python nes-bot/tools/batch255.py --launcher <launch.sh> --run-dir <dir> --dir <dir> --seeds ...
```

The seed is the number of frames the bot waits on the menu, which sets the piece
sequence. Each run writes a case file, an input journal, decision logs and, after
verification, `case_state: verified`.

Watch a recorded game (uncapped score, level and lines panel):

```bash
nes-bot\tools\watch.cmd 500                 # rebirth game at 500% (about 3.9x is the ceiling with the panel)
```

Uncapped score of a run: `python -m nes_original.theoretical_score <gameplay-seed-N-events.jsonl>`.

## Testing changes quickly

`nes-bot/tools/zone_sim.py` plays just the danger stretches (levels 150–175, 246–255, and the
same on lap 2) with the real decision code and samples crashes from the model. It
matches real games move for move (it plans one frame after spawn, like the real
controller, and builds the same candidate list) and can start from a real board and
piece sequence. Typical use: 300 games per setting, compare pass rates.

## Score bot with playouts (run-score80.sh)

In tetris mode (levels 29-150 and 176-243, stack up to 8 rows) and burn mode, the bot
ranks every (current, next) placement pair, keeps the best 12 (at most 4 per current
placement) and plays each one out over all 49 sequences of the next two unknown pieces,
weighted by the NES piece odds and placed greedily with the same weights
(StackRabbit-style playouts). A playout that tops out scores -1000. The 7 first-piece
cases are shared across the 49 sequences, and the 12 pairs run on 3 threads, so a plan
takes about 10 ms on a cloud core. A plan that still runs past one frame starts late;
with `--late-plan retarget` the controller then checks the chosen board is still
reachable from the new pose and chooses again if not (a late plan otherwise misses
its target at an 8-row stack).

## Learned leaf value (run-score-vnet.sh)

`run-score-vnet.sh` is the playout bot plus a small learned value net. At levels 176-243,
while the stack is at most 6 rows, each playout's final board also gets 12 x V(board),
where V is an MLP (200 cells + 10 column heights, two hidden layers of 128) trained to
predict the discounted clear points still to come from that board (a tetris = 1, a top-out
= -10). Training data comes from simulated 1G games of the playout bot, some with random
moves so the net also sees damaged boards; scripts in `tools/value_net/` (`gen.py`,
`train.py`). The net in use is `weights/value-net-v3.npz`.

The gate matters. On every board, or on tall stacks, the net trades survival for points
(full-lap sim: 82.6M but 70/75 laps survived with the net everywhere, against 75/75 without).
Gated to stacks of at most 6 rows, it gains about 2M per lap at the same survival.

## First input on the spawn frame (run-score-ff.sh)

The feedback controller used to wait for two matching active observations of a new piece
before its first input, so the first input landed one frame after spawn, and the simulator
modelled two neutral frames before any future piece could move. Probes in real MesenCE show
there is no input lag: an input sent on the first active observation moves the piece on the
next frame. With `NES_FIRST_FRAME=1` the controller accepts that first observation when it is
the expected fresh spawn (the orientation the preview showed at lock, x 5, y 0, fall 0), and
`NES_SPAWN_SETTLE=0` makes the simulator, the playouts and the lookahead projection plan from
the raw spawn pose. Each piece reaches about one row higher, which makes a 9-row tetris stack
(`alt_below 9`, weights `tetris-playout12-b9-vnet-ff.json`) safe.

`run-score-ff.sh` sets both variables and its own numba cache folder (numba bakes
`NES_SPAWN_SETTLE` into compiled code). Full-lap sim, 75 laps: 86.1M, 74/75 survived
(score-vnet 83.5M, 75/75). One spawn frame instead of zero is not enough: at 9 rows it
survived 67/75. A 10-row stack gave 86.5M but 48/50.

## Tetris mode at more levels (run-score-wide.sh)

`run-score-wide.sh` is `run-score-ff.sh` with tetris mode also at levels 159-167, 174-175
and 244-248 (weights `tetris-playout12-b9-vnet-ff-wide.json`), and without the lowstack
246-249 zone. The crash model already rates tetrises at those levels as safe, and the
CrashMapPrioritizer still vetoes the risky ones. 151-158 and 168-173 stay as before: tetris
mode at 151-155 too died 7/50 (crashes at 154 and 157). Full-lap sim, 75 laps: 89.7M,
75/75 (`run-score-ff.sh` 86.1M, 74/75). Most of the gain is in the 154-175 band (1.6M to 3.9M).


## Doubled hole weights in tetris mode (run-score-holes.sh)

`run-score-holes.sh` is `run-score-wide.sh` with the tetris-mode `holes`, `hole_rows` and
`covered` weights doubled (weights `tetris-playout12-b9-vnet-ff-holes.json`; burn and
zone weights unchanged). At levels 174-243 the wide bot made about 114 hole-adding
placements per lap, and 92% of them had a hole-free option. Full-lap sim, 100 paired
laps: 100/100 survive, about +2.4M per lap (92.0M vs 89.6M). Tried and not kept: hole
weights x1.5 (+1.7M), x2.5 and x3 (worse, deaths), doubling the burn-mode hole weights too
(48/50), a 10-row stack at 176-235 (+0.5M, 2 extra deaths), and a playout penalty for
burning a ready tetris (+0.9M in sim, but all 3 real games below score-wide).

## Tetris mode at 250-252 and 254 (run-score-top.sh)

`run-score-top.sh` is `run-score-holes.sh` with tetris mode also at levels 250-252 and 254
(weights `tetris-playout12-b9-vnet-ff-top.json`, alt levels 29-150, 159-167, 174-248,
250-252 and 254) and without the Dellacherie 250-254 zone. Line clears at 250-254 do not
crash in the cycle model, so the old safe-play zone there only cost points. Tetris mode at
all of 249-254 earned more (+2.1M per lap) but died too often: 1.8% of 780 replays from
level 245 (crashes at 249, top-outs at 253-254), and 30/40 five-lap games. Skipping 249 and
253 cuts that to 0.4% (hole bot 0.13%) and keeps about +1.45M of the gain. Five-lap sim, 40
games (seeds 30000-30039): 35/40 survive all 5 laps (score-holes 32/40). Also tried: a
5-row stack cap at 249-253 (same deaths, less score).
## Tetris mode from level 18 (run-score-start.sh)

`run-score-start.sh` is `run-score-top.sh` with tetris mode also at the start levels 18-28
(weights `tetris-playout12-b9-vnet-ff-start.json`, first alt range 18-150 instead of 29-150).
Gravity there is 2-3 frames per row, so the 1G tetris weights are safe. Before, those levels
made no tetrises. Simulator: levels 18-28 earn 0.94M instead of 0.21M (tetris share 0% to 56%):
+0.75M ±0.01 over the first 400 lines of 200 paired games (200/200 survive), and +0.49M ±0.39
over 96 paired full laps (98/100 for both). Tetris mode up to 153 lost points and added deaths.

## No risky crash-zone clears below 14 rows (run-score-safe157.sh)

`run-score-safe157.sh` is `run-score-start.sh` with `NES_RISK_BUDGET=17:.9,14:.5`. That drops
the 11-row tier of `crash_model.RISK_BUDGET`, under which a stack of 11-13 rows could take a
clear the cycle model rates up to 30% fatal. In five-lap sims most level-157 deaths came from
this: during an I drought the stack reached 11 rows in the no-singles zone, and the bot took a
25% single. The default budget is unchanged. The env var is read when `crash_model` is
imported, so only this launcher uses it. Five-lap sim (ideas thread): on 80 paired seeds with
the 8-row stack, 157 crashes fell from 5 to 1 (75/80 vs 72/80) at the same score. With this
bot's 9-row stack, on 80 paired seeds against the same bot without the budget change
(score-start): 66/80 against 63/80 five-lap games survived (96.0% vs 95.1% per lap), with the same
score (+0.00 ±0.04M per lap). The 3 extra deaths without it are all level-157 crashes, and the fix
adds no deaths of its own. One real game (seed 957) crashed at level 253 with a 15-row stack, after a
drought left no safe move. That crash had nothing to do with the budget, and the rerun reached
level 255.

## Known limits

- About 5% of games still fail, mostly around level 157 (singles there carry at least
  25% crash risk, so the bot needs doubles or more at top speed).
- The crash model's lap-2+ predictions are untested beyond the one rebirth game.
- Points: about 45% of lines in the tetris bands come from tetrises; the per-lap ceiling
  is about 140M with the crash zones played safe.
- Results are verified in an emulator, not on hardware.
